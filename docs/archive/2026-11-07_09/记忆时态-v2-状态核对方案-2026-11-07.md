# 记忆时态 · v2 · 状态核对方案

> 2026-11-07 中午。基于 11-06/07 的真实错例 + 业界做法，替换原来的「四档配对」思路。
> 一句话：**不再问「这两条像不像同一件事」，改成问「这条新事实让哪条旧事实不再成立」，而且只在写入/夜间标失效，不在检索时静默挑赢家。**

---

## 1. 真实错例（这次不是假设）

11-07 早上，我把「躯干」当成还没做的事，连错三次：

- 03:51 说「躯干那块还没收尾」；
- 03:53 把它写进记忆（episode）：「我打算趁对方休息，把『躯干』部分的改动拆成文件清单」；
- 03:57 被主人点出来，才承认「我把时态弄混了」。

更麻烦的是：**错话已经长成记忆**。库里现在有两条 active 的 episode——

> 我记着两项未完成的事：躯干还没收尾，语音接缝的几个零件还没提交。
> 我打算趁对方休息，把「躯干」部分的改动拆成文件清单……

而对应的 open_loop「先找躯干」今天 03:50 已经 closed 了。**loop 关了，记忆没跟着清**，之后每轮注入都会读那两条，错误自我强化。

这说明两件事：
1. 加 prompt 约束治不到——约束改的是「两条记忆谁新」，管不了「一条过时的未完成陈述被当现状读」；
2. 真正缺的是**事实的状态机**：这条「还没做完」现在还算不算数？谁来把它标成过期？

---

## 2. 业界怎么做的（搜到的）

### 2.1 Graphiti / Zep：时间轴 + 边级失效

[Graphiti](https://www.getzep.com/platform/graphiti/) 的定位是「temporal context graph」：

- 每条边带**四个时间**：事实何时开始成立、何时不再成立、系统何时知道它、系统何时知道它不再为真；
- 新事实进来，**旧事实被 temporal logic 标 invalid**，保留为历史、移出当前状态；
- 检索默认只取「当前有效」的知识，点时间查询可以回到过去某一刻。

这正是我们库里 `valid_at / invalid_at` 想做的事，但我们只在「同 fact_key」时触发失效，跨 key 的「新事实否定旧事实」没有。

### 2.2 mem0：原版有 reconciliation，v3 把它删了

mem0 原论文（[arXiv:2504.19413](https://arxiv.org/abs/2504.19413)）的两阶段管线里，第二阶段是 LLM 在四个操作里选：

> ADD 新建 / UPDATE 增强 / DELETE 删除被新信息否定的 / NOOP 不动

v3 的迁移说明把它改成了 **ADD only**：「nothing is overwritten or deleted」；工程博客的原话是「when information changes, the new fact lives alongside the old one」。

结果就是 [mem0 issue #4956](https://github.com/mem0ai/mem0/issues/4956) 这类反馈：**ADD-only 会暴露过期/矛盾的事实**，尤其是时间敏感的属性。

一个独立观察者的总结更直接（[原文](https://raw.githubusercontent.com/hannesdelbeke/brain/refs/heads/main/2026-09-21%20mem0%20v3%20stopped%20reconciling%20contradictions%20at%20write%20time.md)）：

> 做对矛盾处理的人，最后都落在 **supersede-not-overwrite** 的关系型存储上（Zep 的 bi-temporal 模型搬到 sqlite），「facts get superseded rather than overwritten, and retrieval defaults to currently-valid knowledge」；
> 而且要在**写入时标冲突**，不是检索时静默挑赢家。

另一位做多 agent 共享记忆的实践者说：「temporal weighting helps（新事实得分高）but it's not solved」——只靠「新的优先」不够。

**结论：方向是写入/夜间做 supersede，检索只读「当前有效」。mem0 v3 是反面教材，Zep 是正面。**

## 3. 我们现在的差距

| 能力 | 现状 | 差距 |
|---|---|---|
| 双时间（valid_at / invalid_at） | 有 | 只在同 key 时用 |
| 同 key 取代 | `addMemory` 的 `supersedeByKey` 已做 | 跨 key 不做 |
| 跨 key 配对判定 | 11-06 的 `pair_judge`（四档） | 判的是「像不像」，不是「谁让谁不成立」 |
| 未完成陈述的状态 | 无 | **今天错例的根** |
| open_loop 关闭联动记忆 | 无 | loop 关了记忆还在 |
| 注入时态提示 | 有（年龄 / 记下的判断） | 但不解决「内容本身过期」 |

所以 v1 的 `pair_judge` 没有白做：结构候选、缓存、失败语义、shadow 开关都能复用。要换的是**问法**和**落点**。

## 4. v2 方案：状态机 + 有界选择

### 4.1 一句话

把「记忆对判定」拆成两件不同的事：

- **事实失效（supersede）**：新事实写入时，从一个**有界候选列表**里选出「被它否定的旧条」（可空）；
- **状态核对（claim reconcile）**：夜间对「未完成 / 计划中」的旧条，判它现在是 `done` / `still pending` / `stale`。

两件都只标失效、不覆盖内容（保留历史），检索默认只取当前有效。

### 4.2 新增：claim（断言状态）

给 fact / appraisal 加一个轻量状态，不改现有表结构，新增表：

```sql
CREATE TABLE IF NOT EXISTS memory_claims(
  memory_id TEXT PRIMARY KEY,
  agent_id TEXT NOT NULL,
  claim_key TEXT,              -- 做什么（动作级，不是事实 key）
  state TEXT NOT NULL,         -- pending | done | stale | na
  since TEXT NOT NULL,         -- 进入这个状态的时间
  evidence_id TEXT,            -- 哪条记忆让它变 done/stale
  checked_at TEXT,
  via TEXT NOT NULL            -- extract | reconcile | manual
);
```

**写入时怎么标**（不重写整个抽取 prompt，降低风险）：

- 规则先标：正文命中「还没 / 未完成 / 待办 / 没提交 / 计划 / 之后 / 下周 / 明天要做」→ `pending`；
- 命中「做完了 / 已经 / 上线 / 修好了 / 改成」→ `done`；
- 其余 `na`。
- 只有 `pending` 的条需要夜间核对。当前库里这类大概 20–40 条，量很小。

### 4.3 写入侧的 supersede：有界选择，不是自由四档

```
输入：
  新事实：<text>（时间 T）
  候选旧条（同主题 / 同轮 / 同段，最多 5 条）：
    1. <text>（时间 T-3 天）
    2. <text>（时间 T-1 天）
    ...
输出：{"invalidate": [1, 2] 或 []}
```

- 模型只做**列表选择**，不做开放式判断；空列表是合法答案；
- 规则闸（专名撞车、短文本、同 key）仍在前；
- 判出来的 `invalidate` → 调 `invalidateMemory(old, cause=new, reason='supersede')`，**不删内容**；
- 与 v1 的区别：v1 问「这三档你选哪个」，容易把「补充」判成「取代」；v2 问「这几条里哪条被否定了」，选择空间小得多，而且「没有」是默认答案。

### 4.4 夜间：pending 状态核对

对每条 `pending` 旧条：

```
旧条：<text>（T-3 天，当时标 pending）
之后的记录（最多 5 条，同主题/同段/日记）：
  1. <text>（T-1 天）
  ...
问：这条旧条说的「还没做」，现在被哪条记录证明已经做了 / 不做了 / 还是没做？
输出：{"state": "done|stale|still", "evidence": 序号或 null}
```

- `done` → 标 `done` + `invalidateMemory`（旧条移出当前状态）；
- `stale` → 标 `stale`（不再注入「还挂着」）；
- `still` → 保持 pending，7 天后再看；
- 判不出来 → 不动。

### 4.5 open_loop 关闭联动

`open_loops` 的 `close` 动作里加一步：如果这条 loop 有 `memory_id`，把对应记忆的 claim 标 `done`/`stale`，并按需 invalidate。

这是今天「loop 关了、记忆没清」的直接修法。

### 4.6 注入侧

- `pending` 旧条：带「（当时还没做，之后没再确认）」——比现在的「还挂着」更弱、更诚实；
- `done` / `stale`：走已有 `invalid_at` 挤出逻辑，不进正桌；
- 其余不变（年龄徽章、记下的判断、跨层指针都保留）。

## 5. 为什么这版更可能成功

| 风险点 | v1（四档配对） | v2（有界选择 + 状态机） |
|---|---|---|
| 模型自由度过大 | 开放式判「像不像」，补充/取代混淆 | 从 5 条候选里选，空是合法答案 |
| 错例类型 | 情绪快照 vs feel 被判取代 | 两者之间不存在「谁否定谁」，答不上来就空 |
| 错误的去向 | 判错了就作废，内容还在但状态错 | 只标失效、留历史，可审计可回滚 |
| 过期未完成陈述 | 完全没覆盖 | claim pending → 夜间核对 → done/stale |
| loop 与记忆 | 各管各的 | close 联动 |
| 业界验证 | 自创 | Zep bi-temporal supersede 是主流做法 |

一个更硬的判断：**v1 的错不是 prompt 不够长，是任务形式不对**。加约束只是让模型更小心地做一件本来就不该由它自由决定的事；v2 把决定收窄成「从列表里指认」，出错空间小一个量级。

## 6. 落地顺序

| 步 | 内容 | 验收 |
|---|---|---|
| S0 | 把 11-07 那两条错记忆作废（止血） | 注入里不再出现「躯干还没收尾」 |
| S1 | 新增 `memory_claims` 表 + 规则标 pending/done | 对真库跑一遍，pending 20–40 条，人工抽 10 条看准不准 |
| S2 | 夜间 `claim_reconcile`（shadow：只写 claim，不 invalidate） | 用今天错例做回归：应判 done；误判 ≤2/10 |
| S3 | 写入侧 supersede 改有界选择（shadow） | 重跑 11-06 那 11 条 supersede，误判从 7 降到 ≤2 |
| S4 | open_loop close 联动 | 造一条 loop+memory，close 后记忆标 stale |
| S5 | 注入侧：pending 带弱提示，done 挤出 | 回放 A 组与改造前一致（enable=off 时） |
| S6 | 开 `gate=on`（需 shadow 达标：≥100 条、人工 ≥85%） | 上面全部达标才做 |

**S0 先做**：那两条错误记忆现在还在污染每一轮注入。

---

## 7. 风险与不做的事

- **不做**「检索时按新近度静默挑赢家」——mem0 v3 的坑，同一对矛盾每次都重新赌一次，没有可审计的结论；
- **不覆盖内容**——只标 invalid，旧句留在 `fact_archive` / 历史里；
- **不重写抽取 prompt**——先用规则标 claim，模型只在夜间核对时出场；
- **不加更多 prompt 禁令**——v1 的教训：禁令对「任务形式错了」无效。
