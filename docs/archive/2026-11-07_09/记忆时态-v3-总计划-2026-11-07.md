# 记忆时态 · v3 · 总计划

> 2026-11-07。综合：这两天跑出来的真实错例、11-06 首轮 11 条 supersede 的误判、业界做法（Zep/Graphiti、mem0）、以及「哪些地方模型调用局部不可省」。
> 一句话：**把「时态」从相似度问题改成状态机问题；模型只在三个窄口出场，其余全用规则和已有结构。**

## 0. 成功怎么算

不靠感觉，四个数：

| 指标 | 现在 | 目标 |
|---|---|---|
| 注入里出现「过期的未完成陈述」 | 有（11-07 躯干那两条） | **0**（回归样本全过） |
| M1 指认式 supersede 误判率 | v1 四档约 7/11 | **≤ 2/10**（人工抽查 30 条） |
| M2 状态核对准确率 | 未测 | **≥ 85%**（人工 30 条） |
| 判定延迟 / 超时 | p50 1.6s、max 4.1s、超时 0 | p95 < 4s，**超时 0** |

达不到就不开 `gate=on`。全部 shadow 先跑。

## 1. 问题清单（按严重度）

**P0 · 错话会长成记忆。** 11-07 我把「躯干还没收尾」当成现状，还写进 episode；对应 open_loop 03:50 已关闭，记忆没跟着清。之后每轮注入读它，错误自我强化。→ 这是「时态」问题里最伤的一种，因为它污染后续所有判断。

**P1 · v1 的任务形式不对。** 让模型自由判「像不像同一件事」，它会把「情绪快照 vs feel」「表情包澄清」判成取代。11-06 首轮 11 条 supersede 里约 7 条错，其中 4 条是「同 key 直判」规则硬造出来的。

**P2 · 跨 key 的事实失效没人管。** `addMemory` 只处理同 `fact_key`；跨 key 的「新事实让旧事实不成立」没有落点。

**P3 · 延迟擦线。** 3s 超时下 max 3004ms、超时 5 次；提到 6s 后超时 0，但 p95 还需要盯。

## 2. 设计原则（七条，全部有出处）

| 原则 | 出处 / 理由 |
|---|---|
| **P1 状态机，不是相似度** | 错例证明「像不像」判不出「还作不作数」；Graphiti 的边带四时间戳，本质是状态 |
| **P2 写入/夜间标失效，检索只读当前有效** | Zep：「Outdated facts are invalidated by temporal logic — preserved as history, removed from current state」 |
| **P3 只标不覆盖（supersede-not-overwrite）** | 实践共识；mem0 v3 的 ADD-only 是反面教材（旧事实与新事实并排活） |
| **P4 有界选择** | 模型从候选列表里指认，允许答「没有」；比开放式四档稳一个量级 |
| **P5 规则先行，模型只兜灰区** | 同 key / 专名撞车 / 短文本 / 时间比较全部规则化，模型不碰 |
| **P6 失败即退回** | 超时、假 JSON、复核不一致 → uncertain，绝不改记忆 |
| **P7 shadow 先行、可回放** | v1 的教训：先只观察，数据够了才允许动手 |

## 3. 模型调用清单（局部不可省）

这一节是核心：**哪些地方必须调模型、输入输出是什么、为什么不能省、怎么兜底**。

### M1 · 写入时「谁让谁不成立」（不可省）

- **位置**：`gate.applyWrite` 的后台队列（不阻塞写入）
- **触发**：`action ∈ {new, conflict}`，且候选池非空，且未命中规则闸
- **输入**：

```
新事实：<text>（2026-11-06）
候选旧条（最多 5 条，按结构相关度排序）：
  1. <text>（2026-11-03）
  2. <text>（2026-11-05）
  ...
```

- **输出**：`{"invalidate": [1, 2]}` 或 `{"invalidate": []}`
- **为什么不可省**：跨 key 的「这条是否让那条不再成立」只有语义能判；规则只能覆盖同 key 和状态词对。
- **预算**：每天约 5–15 次（写入量 147 条/天，结构候选命中约 10%）；单次 p50 1.6s。
- **缓存**：`pair_key = sha1(agent|old_id|old.version|new_id|new.version)`，判过不再问。
- **兜底**：超时 / 假 JSON / 复核不一致 → `uncertain`，不标失效；`too-short`（<12 字）、专名撞车直接跳过。
- **复核**：只对「要动手的」再问一次，两次都指认同一条才认。

### M2 · 夜间「pending 还算不算数」（不可省）

- **位置**：`nightly` 新步骤 `claim_reconcile`
- **触发**：当天有 `memory_claims.state='pending'` 的旧条，且距上次核对 ≥ 3 天
- **输入**：

```
旧条：<text>（2026-11-03，当时标「还没做完」）
之后的记录（最多 5 条，同主题/同段/日记）：
  1. <text>（2026-11-06）
  ...
```

- **输出**：`{"state": "done|stale|still", "evidence": 序号|null}`
- **为什么不可省**：判断「这件事后来做完了没有」需要语义；规则只能看到「做完了」这种词，看不到「已经变成零件体系了」。
- **预算**：pending 条数 × 1 次/天（当前预计 20–40 条，约 1 分钟）。
- **兜底**：判不出 / 证据不明确 → `still`，7 天后再看；绝不作废。

### M3 · 灰区 claim 标注（默认不调，备选）

- **触发条件**：规则能标 80% 的 pending/done；只有「之前说要 / 后来好像做过」这种含糊句，规则标 `na`，不强行调模型。
- **启用条件**：S2 跑一周后，若人工抽查发现规则漏标 > 15%，再启用。
- **为什么放后面**：避免一开始就把模型塞进每条记忆的写入路径；能用规则的地方别花模型。

### M4 · 复核（可省，但建议留）

- **位置**：M1 判出 `invalidate` 之后
- **输入输出**：同 M1，只问「刚才这几条，确定被否定了吗」
- **成本**：只对少数要动手的对，约每天 1–3 次
- **兜底**：不一致 → 不标

**明确不调模型的地方**：注入路径（预算几十毫秒）、同 key 取代（addMemory 已做）、纯时间比较、短文本、专名闸。

## 4. 数据模型

只加表、不 ALTER 老表：

```sql
CREATE TABLE IF NOT EXISTS memory_claims(
  memory_id TEXT PRIMARY KEY,
  agent_id TEXT NOT NULL,
  claim_key TEXT,              -- 动作级（如「躯干拆解」「语音接缝提交」），可空
  state TEXT NOT NULL,         -- pending | done | stale | na
  since TEXT NOT NULL,
  evidence_id TEXT,            -- 哪条记忆让它变 done/stale
  checked_at TEXT,
  via TEXT NOT NULL            -- extract | reconcile | manual
);
CREATE INDEX IF NOT EXISTS idx_claims_agent_state ON memory_claims(agent_id, state);
```

复用：
- `memory_items.invalid_at`（已存在）→ `done`/`stale` 时调 `invalidateMemory`；
- `open_loops.memory_id`（已存在）→ loop 关闭联动。

## 5. 四条链路

### 5.1 写入侧（改 `gate.js`）

1. 规则先标 claim：正文命中「还没 / 未完成 / 待办 / 没提交 / 计划 / 之后」→ `pending`；命中「做完了 / 已经 / 上线 / 修好」→ `done`；否则 `na`。
2. `applyWrite` 判 `new/conflict` 后，按现有结构候选 → 调 M1（有界指认）→ 只标 invalid，不删内容。
3. 全程 shadow：先只写 `memory_claims` 与事件，不动 `invalid_at`。

### 5.2 夜间（改 `nightly.js`）

新增步骤 `claim_reconcile`，放在 `stale_judge` 之后：

1. 取 `pending` 且 ≥3 天未核对的条；
2. 找之后的相关记录（同主题 / 同段 / 日记 / 同 turn）；
3. 调 M2；`done` → invalidate + 记 evidence；`stale` → 只改 claim；`still` → 更新 checked_at；
4. 无模型/全判不出 → 步骤 `ok:true, skipped`。

### 5.3 open_loop 关闭联动（改 `loops.js`）

`closeLoop`（或等价函数）里：
- 若 `memory_id` 存在，把 `memory_claims.state` 改成 `done`，并 `invalidateMemory`；
- 写事件 `loop.closed_memory`，方便审计。

### 5.4 注入侧（改 `index.js` 三处接线）

- `pending` 旧条：把「还挂着」换成「（当时还没做，之后没再确认）」——更弱、更诚实；
- `done` / `stale`：走已有 `invalid_at` 挤出，不进正桌；
- 其余不变（年龄徽章、记下的判断、跨层指针）。
- **`enable=off` 时，注入输出必须与改造前逐字一致**（回放 A 组对照）。

- 验收：M1 误判 ≤ 2/10；候选列表构造正确；无候选不调模型。

### S4 · loop 关闭联动（0.5 天）

- 验收：造 loop+memory，close 后记忆 invalid；事件可查。

### S5 · 注入侧窄改（0.5 天）

- pending 弱提示；done/stale 挤出。
- 验收：`enable=off` 回放 A 组逐项与改造前一致；`enable=on, shadow` 时注入文本只多「当时还没做」那半句。

### S6 · 开 `gate=on`（门槛制）

前置：S2/S3 shadow ≥ 100 条判定、人工 ≥ 85%、超时 0。
- 先开 claim 的 invalidate（夜间路径），再开写入侧 supersede。
- 每次只开一项，观察 3 天；任一项误判超线 → 退回 shadow。

## 8. 风险

| 风险 | 兜底 |
|---|---|
| 模型把「补充」指认成「失效」 | 有界列表 + 复核 + shadow；只标不删，可翻账本 |
| 规则误标 pending（把「已经」标成 pending） | 只影响夜间多问一次，不会改记忆；S1 人工抽检 |
| 夜巡变慢 | pending 20–40 条 × 1.5s ≈ 1 分钟；设 `claim.daily_max=60` |
| 两个机制打架（v1 四档 vs v3 指认） | S3 上线后，v1 的 `memory.judge.gate` 只保留 shadow，不再作为动作来源；事件分开记 |
| 新表写坏老库 | 只 `CREATE TABLE IF NOT EXISTS`，不动老表 |
