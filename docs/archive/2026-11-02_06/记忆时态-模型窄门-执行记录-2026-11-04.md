## 2. 修掉的 bug

### 真 bug（会影响生产）

**① 提取路径的 `fact_key` 从未传给门控** —— `features.js:430` 只传 `key`，而 `gate.js:123` 只读 `cand.fact_key`。
后果：门控的「同 key 原地改写」分支**从来没生效过**，旧条全靠 `addMemory` 的 `supersedeByKey` 兜底；
P0 基线里「实际会挤出 = 0」有一部分就是这个原因。
修法：`fact_key` 与 `key` 一起传（`features.js:430-437`）。修完 `write-gate-judge` 用例⑦验证：同 key 现在真的走 update，旧句进 `fact_archive` 留底。

**② 超时定时器 `unref`** —— `pair_judge.js` 初版 `withTimeout` 给定时器加了 `unref()`。
后果：没有其它句柄时进程直接退出，超时永远等不到（P1 测试当场挂住）。
修法：去掉 `unref`，只 `clearTimeout`。

**③ `judgeDay` 参数签名接错** —— `nightly.js` 里按位置参数调用，而它只收一个对象。
后果：夜巡永远扫到 0 行，静默不报错。
修法：改成对象调用；P3 测试用「rows ≥ 2」抓住。

**④ 弱标死分支 + 审计脚本跟着空转** —— `passport.js:212` 的 `s.source === 'topic_weak'` 永不成立（`stampRow` 只产生 invalid / topic_key / topic_state）；`audit-weak-stale.mjs` 也查同一字段。
后果：那份「弱标抽查」一直导出 **0 对**。
修法：删死分支；审计脚本改查 `s.weakLater`。修复后立刻导出 **51 对**可人工过目的候选。

**⑤ INV10 表白名单漏登记** —— 新表 `memory_pair_judge` 没登记，全量测试 `表白名单 CI` 报 560 中 1 条失败。
修法：`src/ports/ownership.js` 的 `writegate.tables` 加上它。

### 测试自身的错（不是产品 bug，但记下来免得下次再踩）

- `packInjection` 按 `partition` 分桶，直接传 `memory_items` 行会被**静默丢弃**；
- `stampRow` 的 `occurred` 读 `memory_timeline.valid_from`，不是 `created_at`；
- `addMemory` 对同 `fact_key` 会当场作废旧条，所以「两条 active 同 key」只能用原样插入造；
- P2 之后新库自带 `memory_pair_judge`，「没缓存表」要手动 `DROP TABLE` 才测得出来。

## 4. 「能认清时间了不」——分三层回答

**第一层：知道这是哪天的。** 本来就能，这次没动。年龄徽章覆盖 85%，关掉它裸暴露从 8 跳到 77。

**第二层：知道「现在还算不算数」。** 以前几乎判不出来（明确时态 1.2%）。现在有了判定的**动作**：
结构候选（同 key / 同主题 / 同轮 / 同段）→ 专名闸 → 模型四档 → 缓存 → 只有 supersede 才允许作废。
模拟里 12 对四档各 3 对全对；`on` 只动 3 条 supersede，补充/无关/不确定一条没动。

**第三层：真实数据上开没开。** **没开。** `memory.judge.enable` 默认 off，真库还是 off。
按计划的闸门：先开 `enable=on + gate=shadow` 跑一周，攒 ≥100 条判定，人工抽查 30 条一致率 ≥85%，再拨 `gate=on`。

所以准确的回答是：**她现在有分清时间的能力了，但还站在「只观察、不动手」的位置上。**
要不要走到「真的按判定退休旧说法」，得看 shadow 数据——这一步我没替她按下去。
