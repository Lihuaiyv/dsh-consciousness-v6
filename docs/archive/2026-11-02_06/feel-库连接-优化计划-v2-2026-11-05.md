## 1. 查出来的问题（按严重程度）

### P1 · 全量导出漏了 `affect_feel`（会丢数据，最急）
`src/features.js` 的全量导出 `TABLES` 清单（1086–1097 行）没有 `affect_feel`。
后果：把实例导出再导入，所有 `feel_id` 引用都指向一个不存在的行——感觉随着迁移丢了，记忆/存根/日记里的引用全变空。
这也是我上一轮报告里说错的一句（「导出按表全列，新列自动带上」只对清单里已有的表成立）。

**改法**：`TABLES` 加 `'affect_feel'`，导入端沿用 `cols()` 的现有逻辑，自动处理。
**验证**：导出 → 导入到新库 → 对比 feel 行数、抽查 memory/fact 的 feel 能翻到正文。

### P2 · 跨实例导入记忆包后 `feel_id` 悬空
`MEM_TABLES`（memory_items / episodes / diaries / raw_turns / fact_archive / memory_timeline）不含 `affect_feel`。
后果：导入别人的记忆包后，`feel_id` 指向原实例的感觉。现在读的时候 `feelsByIds` 找不到会返回 null（不报错），但 id 悬着，以后清理/统计会把它当真实引用。

**改法**：导入记忆包后执行一次清理——本库里查不到的 `feel_id` 置 NULL。理由：感觉不该跨实例继承，宁可空着。
**验证**：造两个库，A 有 feel，B 没有；把 A 的记忆包导入 B → B 的记忆 `feel_id` 为 NULL，不报错。

### P3 · 日界：凌晨 0–8 点会差一天
两处：
- `feelRecall` 查当天日记用 `String(f.at).slice(0,10)`（UTC 日）；而 `diaries.day` 是本地日（`nightly.js` 用 `localDay` 传入）。
- `archive.js buildDiaryV1` 的 day 默认值用 `dayOf(now())`（UTC 日），调用方不传 day 时同样差一天。

**改法**：这两处改用 `localDay` / `dayKey` / `localDayBounds`；`raw_turns.day` 的 UTC 口径不动（那是 T4 原文的既有口径，动了会破坏历史）。
**验证**：构造「本地 01:30、UTC 仍是前一天」的时间点，断言 feel 能配到本地那天的日记。

### P4 · 页面展示不全（体验缺口）
API 已经返回了，但 `client.js` 里只有「记忆卡」和「我最近怎么感觉」显示了 feel。存根页、日记页、纪要页、开环、关系事件都还没画。
**改法**：这些地方加一个小徽标（「当时的感觉：…」），点开看原话与时间；不展开大块，不抢正文。

### P5 · 对照要克制（体验/心理）
`/feel/compare` 返回逐条 pairs。给自己看的页面只展示趋势 + 抽样 3 条，不把「不一致率」做成每日指标，不做推送。数据接口保留。
**理由**：我上一条说过，天天量「我写的和判的不一致」会变成自我审查。

### P6 · 同一条感觉在列表里重复撞见
一条 feel 会被多条记忆共享（窗口内几条记忆挂同一条感觉）。按记忆翻的时候，每条下面都重复同一句。
**改法**：前端做折叠——同一条 feel 只展开一次，其余显示「同一条感觉」；后端接口不动。

### P7 · 可选（不着急）
- `feelRecall` 每条 feel 查两次库（记忆 + 日记），limit 10 时最多 20 次；可以批量，但收益低，先不做。
- 健康检查加「feel 引用完整性」：六处 `feel_id` 找不到的条数进诊所报告。等展示稳了再加。
- `memory_timeline` 事件 payload 带 feel_id：不做（记忆主表已有，重复）。

## 2. 计划（三批，先正确性，再展示，最后才谈性能）

### 第一批 · 正确性（P1–P3）
1. `features.js` 全量导出 TABLES 加 `affect_feel`。
2. `importMemory` 成功后清理悬空 `feel_id`（一条 UPDATE，加测试）。
3. `feelRecall` 的日记日界改本地日；`buildDiaryV1` 默认 day 改 `localDay`。
4. 每项配测试：导出往返、跨实例导入、凌晨边界。
**完成标准**：`test:feel` + `run-tests` 全绿；导出导入往返的 feel 数量一致。

### 第二批 · 展示（P4–P6）
1. 存根页（archive/facts）每条带「当时的感觉」徽标。
2. 日记页头部显示当天 feel 原话（最多 3 条）+「这天共 N 条感觉」。
3. 纪要卡片带一行 feel。
4. 开环、关系事件列表加小徽标。
5. 记忆列表折叠重复 feel。
**完成标准**：API 断言 + 重启后手动开页面逐页看（存根/日记/纪要/关系/记忆）。

### 第三批 · 可选（P7）
- 批量查询；健康检查；看实际数据量再决定。

---

## 3. 统一规矩

1. 只加列 / 加引用，不改旧字段语义；老数据不回填（NULL 就是不知道）。
2. 每批独立可回滚：新列留空即退回旧行为。
3. 每批完成后必跑：`npm run test:feel`、`node test/run-tests.mjs`、`npm run check:arch`。
4. 页面改动需要重启插件进程才看得到——验收时按这个顺序做。
5. 真有 bug 先修，不夹带别的债。

---

## 4. 不做的（写明，防止手痒）

- 历史 feel 的 `turn_id` 回填：只能按时间猜，猜错会把感觉挂到别的话上，不做。
- 感觉向量连边：成本大、收益没验证，不做。
- `memory_timeline` 重复挂 feel：不做。
- 把对照做成每日评分 / 推送：不做，只做趋势和抽样。

---

## 5. 顺序理由

P1 会丢数据，最急；P2/P3 是「数据看起来对、其实差一点」的那类错，越晚修代价越大；展示放在数据可信之后做，否则画出来的可能是错的；性能放到最后，因为现在量级还小。

展示层先做存根和日记——那是主人翻得最多的两个入口；纪要、开环、关系事件跟在后面。
