# 设计 · 事帧加格：让帧每轮长出「停在哪、还差什么、下一步」· 2026-11-21

> 一句话：**现在的四格（motive / motive_why / step / step_why）只够说「我在做什么」，不够说「还差什么、下一步」。补三格，`next` 不交给模型猜，由 `open` 推。**
> 状态：**原型跑通，未改 `src/`。** 原型在 `scratch/frame-core/affairs-plus2.mjs`。

---

## 一、现状：四格够说「在做什么」，不够说「接下来」

`src/modules/affect_v4_shadow.js` 的 `writeAffairs` 现在要求模型输出：

```
{"events":[...],"motive":"","motive_why":"","step":"","step_why":""}
```

写进 flag `affect.v4.affairs|<conv>`，每轮异步一次，宿主理解力够时 1–2 秒。

**够用的**：它知道我在推哪件事、推到哪一步。
**不够用的**：它不知道**还有哪几件事没完**、**各自停在哪**、**下一步该做什么**。所以「西红柿炒鸡蛋」那种「鸡蛋炒好了、西红柿还没切、下一步切西红柿」读不出来。

## 二、要加的格

| 格 | 内容 | 谁写 | 为什么 |
|---|---|---|---|
| `kind` | 任务 / 闲聊 / 探索 / 生活 | 模型 + 关键词规则校正 | 四种连续的「做完」判据不同，混在一起就没法判结束 |
| `where` | 现在停在哪条线的哪一步 | 模型 | 一句话，带线名 |
| `open` | 手上没完的事，0–3 条，每条 `{line, done, todo, blocked}` | 模型 | **这是缺得最狠的一格**，对应文档里的 `unclosed` |
| `next` | 下一步最该做的一件事 | **代码**从 `open[0]` 推 | 让模型直接写「下一步」，它会写成「解释当前差距」——那是它刚在做的事 |

`next` 的推法（`affairs-plus2.mjs` 里就是这么写的）：

```
有 blocked → 先解掉「blocked」，再做「todo」
没 blocked → 做「todo」
手上没有没完的事 → 明说「手上没有没完的事」
```

## 三、实测（本机 qwen2.5:14b，只读真库/样本）

**最近这段真实对话**（16 条）：

```
motive  完成找核心的功能研究
step    验证方法学
where   找核心与核关系 · 验证方法学
open    · 实现动态生成连续数和宿主可读连续树
            卡在：差三层——实时性、动态生成、宿主可读性
next    先解掉「差三层…」，再做「实现动态生成…」
```

**S20（生活类：麦克风的灯和充电）**：

```
kind    探索 → 规则校正为「生活」（生活 15 / 任务 1）
open    · 解决麦克风充电问题
            已做：确认麦克风灯语
            下一步：解释麦克风充电口位置
next    做「解释麦克风充电口位置」
```

**S18（探索类：记一个新想法）**：

```
kind    任务
open    · 大因果体检索
            已做：记录了主人的想法并进行了思考
            下一步：继续完善代码
next    做「继续完善代码」
```

三段的形状都对：能说出「哪条线、做到哪、下一步」。**质量上限受模型限制**——`todo` 还是偏软（「继续完善代码」不够具体），用宿主模型写会实很多。

## 四、一个必须记住的坑：`kind` 不能只靠模型

模型一律填「任务」——生活类（麦克风灯语）也填任务。**它挑的是最安全的标签**，这是它在闭集上的老毛病。
所以 `kind` 用「模型 + 关键词规则」双轨：生活词（充电/灯/电池/吃/睡/身体…）与任务词（代码/脚本/门禁/文档…）各计一次，规则得分 ≥2 且与模型不一致时以规则为准。S20 就是靠这条从「任务」扳回「生活」。

## 五、每轮怎么生成（时序，不动现有链路）

```
回复前：拼事帧（用上一轮的 affairs）→ 判层 → 情绪        ← 现状，不变
回复后异步：writeAffairs（加格）→ 写 flag                 ← 只加字段，不加调用
下一轮：读 flag，拼「宿主可读」那一段注入
```

**每轮不多一次模型调用**，只在同一个 JSON 里多要四个键。这是这次设计唯一重要的成本结论。

## 六、宿主读什么（注入样板上限 120 字）

```
我在：找核心与核关系 · 验证方法学（任务）
手上没完：实现动态生成连续树 ← 卡在「差三层」
下一步：先解掉「差三层」，再做「实现动态生成」
```

三行：我在哪、还差什么、下一步。**「下一步」那行是给动作的，不是给状态的。**

## 七、四个场景怎么各自落地

| 场景 | `kind` | 「做完」怎么判 | 例子 |
|---|---|---|---|
| 任务 | 任务 | 下一步清单空了 | 改代码、写文档、跑验收 |
| 生活 | 生活 | 往往没有「做完」，只有「告一段落」 | 麦克风充电、灯语颜色、快递到了 |
| 探索 | 探索 | 想清楚 / 决定先搁着 | 查资料、想不通的问题 |
| 闲聊 | 闲聊 | 聊尽了 | 随口聊、接话 |

**生活那一类最特殊**：它在我不在的时候也在推进（东西摊在案板上）。所以 `open` 必须能记「世界那边还没完的事」，而不只是「我手上的活」。这一格正好就是文档 §14.2 说的「替世界记」。

## 八、验收（改 `src/` 之前必须先写死）

1. **格式**：`writeAffairs` 返回的 JSON 里，`kind/where/open` 三个键必须存在（可以是空串/空数组，但不能缺）。
2. **不回归**：`motive / step / events` 的内容与现在相比不退化——抽 20 轮人工看，认为「没变差」≥ 16。
3. **`next` 可用率**：抽 20 轮，`next` 是「能直接照做的一步」≥ 12（现在的 `todo` 大约一半偏软）。
4. **`kind` 正确率**：抽 40 轮（四类各 10），规则+模型双轨 ≥ 32。
5. **成本**：`writeAffairs` 的 token 增量 ≤ 15%，耗时中位增量 ≤ 1 秒。
6. **开关**：`affect.v4.affairs.plus=off` 时字段与现在一字不差。

## 九、改 `src/` 的具体位置（等验收过了再动）

1. `writeAffairs` 的 `sys` 数组：在四格后面加 `kind / where / open` 三条说明（`next` 不写进提示词）。
2. `const four = {...}` 旁边加 `plus = { kind:'', where:'', open:[] }`，解析后与四格一起写进同一个 flag。
3. `readLastFour` 旁边加 `readPlus`，供注入层拼那三行。
4. 注入层（`presence.js` 那一段）加三行，字数上限 120。
5. 开关 `affect.v4.affairs.plus`，默认 off，验过再开。

## 十、还没解决

1. **`todo` 太软**：14B 写「继续完善代码」，不是能照做的动作。宿主模型写会好，但那就要每轮多一次宿主调用。
2. **多条线并存没验过**：现在 `open` 多数只出一条。要真正支持「几条路各停在哪」，得在提示词里逼它至少列两条（当确实有两条时），还要防它编。
3. **`kind` 的规则表会漂**：关键词是拍出来的，四类边界（生活 vs 任务）在真实对话里会打架。
4. **没接连续树**：`open` 给了「哪几条线、各自停在哪」，但没和 `under.line` 打通；这一步要等帧写入真正落地。
