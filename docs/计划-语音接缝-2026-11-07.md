所以现在的事实是：本仓的两份是「零件」，外面那份是「生产」。两份都在，这才是要收拾的东西。

## 1. 为什么不直接 import

两个插件是两个仓、两个包。`import '../工具/.../lib/stt.js'` 等于把别人的内部文件当契约——违反 INV10（单向依赖）和 5.1.2（别处不许再抄一份，也别绕开入口）。

桥是链外的宿主管道，它只该认**一个入口名**，不该认别人的文件路径。

## 2. 接缝长什么样

本仓把两个零件包成两个宿主服务，名字先定死：

- `voiceIn.transcribe({ audio, ext, language }) → { text, audioSeconds }`
- `voiceOut.speak({ text }) → { audio, format }`

桥那边只做一件事：`ctx.get('voiceIn')`，拿到就用，**拿不到就明说「没装语音零件」**，绝不回退到自己再抄一份。

服务不落表（两个零件都不写库），所以接缝上没有迁移、没有回退数据，只有「装没装」。

## 3. 改哪几处（三个 commit 的量）

1. **本仓**：新增 `src/voice_service.js`，把 `transcribeVoice` / `synthesizeVoice` 包成服务。这个文件是宿主装配，按术语表**不立零件**，只写进 `host` 域的 `entry`。
2. **桥**：`lib/stt.js`、`lib/tts.js` 删掉实现，改成调服务；找不到服务 → 人话报错（「没装听/说零件」），不静默。
3. **桥**：配置里的嗓子名 `openai` 改叫 `compat`（对齐 INV9：厂商名不进代码），默认的厂商地址删掉，地址必须自己填；老配置要兼容读一次，写进 CHANGELOG。

## 4. 验收

本仓：五道界桩 + `npm test` 全绿，考卷分数不变（27/27、27/27）。

桥：它自己的测试全绿，再加一条真机走查——发一条语音进来、让它回一条语音出去。

判据（能一句话说清）：桥的 `lib/` 里**不再出现** `ffmpeg`、`16kHz`、`<speak` 这些词；本仓两个零件的日志里**能看到被调用**。

## 5. 风险

- 宿主服务是**跨包契约**，形状一改两边都要动。所以先把上面的形状写死，再写实现——别边写边改形状。
- 桥的老用户配置里 `ttsProvider: 'openai'` 会失效。迁移时读一次旧名、写回新名，CHANGELOG 记一行；不静默失败。
- 桥里那份副本删掉之后，如果本仓服务没装上，语音就**彻底不响**。所以桥的报错必须点明「没装零件」，不能只说一句「失败」。

## 6. 这一刀不做

- 不把桥并进本仓（两个插件服务不同的人：一个是 QQ 管道，一个是意识体本体）。
- 不在本仓再写一份「发 QQ 语音」的实现（那正是 5.1.2 要拦的）。
- 不做流式（边说边出字是 `ear` 的下一版，不是接缝的事）。
- 不碰 `record` 段格式（那属于「发信」和桥自己的通道细节）。
