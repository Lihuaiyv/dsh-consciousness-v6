## 二、硬断点（不补，落地第一步就断）

### 1. `turn_ids` 的形态
- 文档例子 `[8812, 8823]` 是 SQLite 隐式 rowid；现库 `chat_turns.id` 是 `TEXT`，`nid('cht_')` 生成（`db.js:200` / `features.js:1440`）。
- 11-11 真跑出来的 18 件（`tmp_1111_events.json`）用的**已经是** `cht_cf3c6b0aa3` 这种，说明只是文档例子没跟上。
- 「想深了回原文」应直接查 `chat_turns`（同表有 text/时间/conversation_id），**不需要** join `raw_turns`——`raw_turns.turn_id` 是 `turn_*`（`extract_queue.js:21`），和 `cht_*` 没有列可 join。第三层 ±2 轮按 conversation_id + created_at 取。

### 2. `settle` 的指认链
- 浮现行只给一句文本 + 半句提示，**不带 id**；`feel` 的 `settle` 只是 boolean（`src/modules/actions/index.js:585`），调用时只传 note（`:609`）；`settleEmotion` 于是默认落到「最近一条还开着的 episode」（`emotion_event.js:156`）。
- 全库 `affect.settle` 事件 **0 条**——不是按钮坏，是无从指认。
- 必须一次改三处：浮现行带事件短 id（如 `E12`，不进抓手词）→ `feel` 加 `settle_event_id`（缺省用「刚浮现的那件」）→ 事件 settle 清 r 和天花板，episode settle 仍只降 intensity，两者不互相冒充。**§8 不能单列一步，它和 §4 渲染是同一个契约。**

### 3. §3.3「按 turn_ids 落在区间内」取情绪瞬间
- `affect_episodes` 没有 `turn_id`、没有外键；唯一的连接是 `cause` 文本全等（`features.js:420`）。
- 改按 `started_at/ended_at` 时间区间取（现库约 55 条/天，分辨率够）；或者给 affect 表加 turn_id（改动更大）。文档口径不改，实现者会去找一列不存在的列。

### 4. 与现有 `episodes` / 日记撞车（全篇没提）
- 库里已有的「事」：`episodes`（纪要，session×day；11-11 有 11 条，`index.js:1366` 每 6 轮压一次）+ `diaries`（一天一篇）。新的 `memory_events` 再切一层「事」，三套边界、三份叙事。
- 注入时日记/纪要/新事件会互相打架，且没有去重键。
- 要么明确 `memory_events` 是「事」的唯一层、`episodes` 降为原料（加 `event_id`），要么写清三者分工 + 注入优先级（事件 > 纪要 > 日记，同 `turn_ids` 去重）。`memory_events` 这个名字也容易和 `episodes` 混，建议叫 `memory_events` 时同步加注释。

## 三、逻辑洞（会把老问题放回来）

### 1. §5 触发第 2 条在主人对话里恒真　【高】
18 件样例 `who` 全是「主人」，「那件事是他说的、这次说话还是他」每轮都成立 → 触发退化成「想头 ≥ 0.5 就浮」，§9 里「不要求触发时凌晨三件永远霸榜」的防线正好被拆掉。
第 3 条「情绪同向」也没定义：现有 8 个标签里 joy/curious/irritated/confused 占七成半。
**改**：删第 2 条，或改成「同一个人 **且** 话题/情绪也变了」；第 3 条写 exact label + `|slow|≥0.2` + 每件 24h 一次；总触发写成「词 OR（人 AND 情绪）」。

### 2. §7 没有全局最小间隔　【高】
唯一限制是「每轮最多一条」。**§9 脚本里其实藏了 `gapMin=20`**（`_cmp.mjs:13/23`），设计正文没写。
另外「浮现后 −0.4」是裸减：r=0.9 的重事浮完还剩 0.5，下一个命中马上又能浮。
**改**：加全局 `min_gap`（先 90–120 分钟）+ 同件 24h 冷却；浮现后 `r = min(r, 0.5) − 0.4`；把隐藏的 20 分钟写进文档。

### 3. §3.2 的 `status` 与 §3.3「不靠猜」自相矛盾　【高】
JSON 让模型写 `status:"没过去"`，§3.3 又说过没过看 episode 怎么结束。11-11 的 fixture 里还留着第一版的 `my_feel`——说明 v2 没重跑过。
而且「被挤掉 = 没完」结构上有偏：一段里只有最后一条情绪会 faded，中间的事几乎全被判「没完」，w 普遍偏高。
**改**：删模型 `status`；写死合成规则（窗口内最强那条 episode 的 resolution：superseded→没过去 / faded→过去了 / folded→放下了；无 episode→unknown，不猜）；抽 10 件对照原话人工验。

### 4. §9 的数字不是文档那套模型　【高】
我跑了 `_cmp.mjs`：6 / 4 / 4 / 5 和 §9 表逐行对得上。但脚本用的是
`rate=0.06×(0.5+peak)`、`cap×0.9`、`birth=0.2×(0.6+peak)`、**cue-only**、gap 20 分钟；
文档写的是 `r0=0.06×(0.5+w)`、天花板 `×(0.6+0.35w)`，还多了提及项、人/情绪触发、周沉底与复活。
**改**：要么按 §6 重跑再下结论，要么把「定下的 −0.4 / ×1.2」降级成「暂定」。

### 5. 参数空　【中】
想头初值「≈0.2~0.3（按 w 给起点）」没公式；天花板初值、复活候选的「沉底」定义、被提到 2 次在 0/0.5/1 里的映射，都没写；「缺口同向」怎么算也没写（deficit 有现成缺口，事件→缺口的映射缺）。
**改**：写死 `r(0)=0.2×(0.6+peak)`、`ceiling(0)=1.0`、`沉底 := ceiling<0.5 或 r<0.05`、次数映射 0/0.5/0.75/1。

### 6. 长段输入　【中】
11-11 一段 1034 条 / 6.9 万字 ≈ 4.5 万 token，本地 32k 模型吃不下；文档没写分块和降级。
**改**：写死输入预算，超了按「时间 + 换目的」切块，逐块切事后按 turn_id 合并；§9 补最长段 token 数。

### 7. 清醒段「≥4 小时没人说话」没定义谁算人　【中】
`chat_turns` 里有 agent 回合、机器 prompt（role=user）、多通道、群聊/陌生人；3 点一条定时提醒就能把整夜切成两段。机器学习消息的过滤写在 §3.2「喂模型之前」，断段在 §3.1——顺序反了。
**改**：只按「主人私聊的人话」算 gap（role=user + `looksNonHuman` 假 + 该会话 person_id=主人）；她和机器消息不参与断段；群聊/陌生人单独成段或标 `who`；切事输入先 `!stranger`。

### 8. 两路老浮现没交代　【中】
§10.5 只点了 episode 那一路（`affect.event.surface`，3 次/天，`index.js:846-862`）；
还有 pulse 的 `surface_queue` 那一路（2 小时一条、一天最多 12 条，`pulse.js`）也仍在跑。
新骨架上线后若不处理，最多三路同时冒。
**改**：§11 步骤 8 写明两路各自的去留；若 pulse 保留，要在同一轮里只允许一个来源。

### 9. 零碎　【低】
- §4.1「我自己想确认」没有入口（没有工具、提示词不带 status）→ 删掉或接 `deepenRecall`。
- §7.1 `mentioned` 由谁判、按什么判没写。
- §6.3 提及计数（30 分钟窗口 + 每天 3 次）/ §6.5 周沉底与复活，既没有表也没有落地步骤。
- §3.1 说「夜里 23:5x 那趟」，实际是 23:00；且「当天的事当天浮不出来」偏轻——白天的事实际要等次日 23:00 切完，隔约 1.5~2 天。

## 四、落地顺序要动

1. **步骤 4 与 8 之间会新旧同冒几天**：把「老实现下线（两路）」并进步骤 4 的同一个开关，8 只删代码。
2. **步骤 4 依赖步骤 6**：骨架上线时 r 还没开始累加，没有候选可浮，验收会误判「设计没用」。把 r 改成读时惰性算 `r(now)`（按 `last_tick`），排到 3/4 之前。
3. **补三步**：提及计数表 / surface 账（含 mentioned）/ 每周沉底+复活（挂 nightly，用 `last_week_at` 幂等）。
4. 先跑一周时，临时文件写 `var\slice-events\<段起>.json` 并记录 token 数，别散在根目录。

## 五、如果只改三处

1. **触发收口 + 全局 min_gap + 同件 24h 冷却**——否则「一天 4 次」只是 18 件那天的瞬态，池子一大就冒得多。
2. **浮现/feel 的 id 契约**——否则 settle 继续 0 次，「放下」永远闲置。
3. **`memory_events` 与 `episodes`/日记的归属和注入优先级**——否则同一件事记三遍、注入互相打架。
