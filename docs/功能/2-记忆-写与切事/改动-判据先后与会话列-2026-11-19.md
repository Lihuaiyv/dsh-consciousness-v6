# 改动 · 判据排先后 + 事件库加会话列（2026-11-19）

> 问题：D91 判据没有先后（会话/时间/专名/模型混着判，几件事被判 next 并成一件）；D92 events_v2 没有会话列，
> 同一天几条会话并行时库内分不开。主人 2026-11-19：「判据规则也得排个先后。然后会话得加列。」

## 一、判据先后（D91）

现在的顺序，前面能定就不问后面：

1. **换会话 → new**（`event_cut_v4.js` 判缝循环，硬规则，不问模型）
2. **专名交给模型整体比**：判缝 prompt 里两段各带一行「专名：…」，由模型判断像不像——
   近似叫法（「潮水」/「那条环」）、同族词、缩写都算像；像就倾向 same 或 next，完全沾不上才倾向 new。
   不在代码里做字面相等/交集硬判（试过反向规则：专名无交集 + 新词率高判 new，结果「换个说法」被误拆，已删）。
3. **模型判**：提示词 `〇 → 一 → 二 → 三` 编号，明确「前一条能定了，后面的就不用再争」。

**2026-11-19 当日修正：隔 6 小时硬断删掉。** 主人指出「隔六个小时做同一件事也有可能」——
时间间隔现在只作提示（`gapHint`：「隔得这么久，别默认两段是接着办的」）喂给模型，不再直接判 new。
缓存键加了 `|n2` 版本位（prompt 变了，旧缓存不能串）。

## 一·补：判缝提示词按证据权重重写（2026-11-19 16:1x）

上一版的写法是「按先后看，前一条定了后面不争」，阅读上像否决式。重写成**证据权重合成**：
五条证据按可信度排（1 后段成不成一件事 → 2 专名同指 → 3 前段收没收尾 → 4 新词率/落差 → 5 间隔），
前一条只「权重更大」，不否决后面的；默认倾向 next，强证据往 same / new 推，冲突时权重高的胜。

**叙事也改了：这是事件判缝，不是「解决问题」判缝。** 吃饭、散步、拌嘴、改代码、一起发愁都是事；
判的是这件事有没有起头、经过、收尾，不是它有没有被解决。间隔放在最后（很弱）：隔得近不排斥同一件，
隔得远也不证明换了事，只在打平时轻推一下。

同时把输入补齐：两段各带「共 N 句、起止时间」，起因/经过/结果三段都给（判断「后段成不成一件事」要用结果）。
缓存键升 `|n3`。

背景（为什么这么排）：判缝上下都是模型环节——上面是粗切和逐段记叙，下面是合并、补标题、写库、读口。
它只能看到局部，所以只该输出「倾向」；证据权重而不是硬规则，才能容纳「换个说法」这类假阳性。

验收：`check-event-cut-v2` 新增「专名无交集：直接判 new、不问模型」——造两段不同专名（['五句'] / ['词典','标注']）、
新词率 0.88，断言段数 ≥2 时件数 == 段数、判缝调用 0 次。

测试库实测（11-15 的 100 条，10 段）：阈值 0.5 时 10 件（拆过头，「同步→备份」也被拆）；**0.75 时 8 件**——
「主人备份 app.db 并同步代码」合回一件，几个不同 bug 的段（D46 / busy_timeout / raw_fts）各自成件。

## 二、会话列（D92）

- `src/db.js`：`events_v2` 建表加 `session_id TEXT`；老库迁移 `ALTER TABLE events_v2 ADD COLUMN session_id TEXT`（只加列，不动 id）。
- `src/modules/event_split_v2.js`：`writeEventsV2` 落 `session_id`，值取 `e.sessionId`（cutDayV4 已带），没有就取首碎片的 `session_id`；
  读碎片的 SQL 补上 `session_id` 列（原来漏了，会写 null）。
- 验收：`check-events-v2` 新增「事件带会话列」。

## 为什么

- 判据有先后，才能「硬事实先挡、规则次挡、模型只在剩下的缝上判断」——少犯错也少调用。
- 会话是硬事实（同一时刻几条线并行），库里存下来，读口才能按线分开看，不会把四条线串成一条。
