# 改动 · 找核影子接全通道（2026-11-23）

> 一句话：切核原来只挂在 `chatReply` 一个口，网页 / QQ / 微信的真对话都不走它——所以重启也不切。
> 现在接到「一轮的账」的统一出口 `writeChatTurns`，所有通道一起覆盖。

## 前情（11-22 初版，合并自 `改动-影子帧-2026-11-22.md`）

初版把 `shadowFrame` 接在 `chatReply` 的 return 之前，只加副表和开关、默认 off。当时验的是：
模块直调一段四句回复 → **2066ms 写 4 行**；`test-chatreply-shadow.mjs` 走完整 `chatReply` → 临时输出打印「接线执行」、`frame_shadow` 4 → 5 行，证明 chatReply 那条路是通的。**但网页真对话不走 `chatReply`，这条证据只覆盖了一个通道**——11-23 才补上所有通道。
两个坑：① 先调函数、函数内部判开关 → 门禁全过但退出码 1（off 时留了异步尾巴），修法是把开关判断提到调用之前；② 测试文本只有一个句号（其余分号）→ 只切出 1 句直接返回，白查半天。

## 为什么

- 网页 / QQ / 微信真对话走 `session/event → captureTurn → commitTurn → writeChatTurns`；`/chat` 与微信主人回合走 `chatReply → writeChatTurns`。
- `chatReply` 只是其中一条通道的入口，挂在它尾部，网页里的真对话就永远到不了。
- 证据：2026-11-23 09:54:09 进程已重启（比所有相关源码的 mtime 新），09:55 / 09:57 两轮真对话之后 `frame_shadow` 仍然 0 行；88 行全是 11-22 17:40 `replay-frames.mjs` 补的。
- 交接原判「差一格：插件进程没重启」不成立；实际是接点挂错口。

## 怎么退

1. 最轻：`flags.affect.frame.shadow = off`（连函数都不调，不留异步尾巴）。
2. 回旧路：删掉 `turn_write.js` 里 `writeChatTurns` 尾部那一行 `shadowTurn(...)`。
3. 注意：旧路（只在 chatReply 调用）本来就不切真对话，不建议退回去。

## 没覆盖的地方（记着，别当没做）

- `writeChatTurnRow`（主动开口 / 工具发信 / QQ 桥出站单行）**不接**：
  QQ 桥出站那一行和 `chatReply` 可能是同一句，两处都切就会切两遍。
  等 QQ 桥真正接上（`attachQQIngest`，现在 index.js 明确没接）再定「同一句只切一次」的规矩。
- 真对话里自动跑要**重载插件**才生效；现在改的是文件，进程里还是旧代码。
