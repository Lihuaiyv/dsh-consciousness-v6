## 二、为什么（一句话）

注入 → `touch` 会把 `last_hit_at` 拨到此刻，而热度里「新鲜度」那一项就是拿它当锚点的 → 新鲜度永远满格。于是**塞进提示词就等于被想起**，越塞越热，越热越先被塞。改成「回复里真说出口才加热」，环就断了。

注意：这一步**不动**那 0.60 的固定底盘（important 满分 + 钉住 + 情绪显著度），也不动重要性锚点名额——那两条仍会常来，见计划第二节。

## 三、怎么验（已验 / 待真机验）

**已验（本机）**

```
node test/heat-on-use.test.mjs      → 通过 6 / 6
node test/run-tests.mjs             → 通过 571 / 571，EXIT=0
```

改前门禁 570/570，改后 571/571（+1 条）。`off` 是默认档，所以**线上行为此刻没有变化**——这条改动现在是「装了闸但没开闸」。

**待真机验（要重启 + 开 shadow 一天）**

1. 把 `memory.heat.on_use` 设成 `shadow`（写 `agent_params`，需主人点头）；
2. 重启加载新代码；
3. 24 小时后看：`surfaced_items` 新增 X 条、`used=1` 新增 Y 条；`events` 里 `memory.heat.shadow` 的 `n` 之和应 ≈ Y，而不是 X；
4. 若 Y/X < 1%，说明「2-gram ≥0.3」判据太严，先调判据再开 `on`；
5. 开 `on` 后 24 小时：抽「汐是夜里涨落的潮水」，看它 `last_hit_at` 被拨了几次（现在一天几百次）→ 应掉到个位数；同时 `retrieval_log` 每轮仍要捞出 4~6 条。

## 四、怎么退

1. 把 `memory.heat.on_use` 设回 `off`（或删掉这个参数）→ 立即回到旧行为，不用回滚代码。
2. 彻底回滚：`git checkout`/手工撤 `index.js` 两处判断 + `surfacing.js` 返回值 + 删测试文件 + 撤门禁那一条；撤完跑门禁应回到 570/570。

## 五、没解决的（别当成修完了）

- **固定底盘 0.60**：`locked` + 重要度 1.0 + salience，跟本环无关，要另开一份计划。
- **重要性锚点名额**（`memory.float.anchor`）：那两条每轮必到的第二个原因。
- **判据可能偏严**：`markSurfacedUsed` 要求 2-gram 覆盖 ≥0.3，换说法复述易漏判 → 所以先 shadow。
- **历史账不平**：库里已有的 `last_hit_at` 是旧机制刷出来的，改完不会自动回退；要归零得另写一次数据修正（属于「数据」不属「代码」，另排）。
- **设置页还没有这个开关的入口**：现在只能改 `agent_params` 里的值。
