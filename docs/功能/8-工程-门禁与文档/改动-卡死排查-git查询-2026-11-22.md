# 卡死排查：一个 Git 查询拖垮了主进程（2026-11-22）

## 现象

不说话的空档也会卡死，几十秒到一分钟，界面一直「正在载入」，重启才恢复。
之前反复查模型、显存、CPU，都没有结论。

## 抓到的证据

用 Windows 自带的 wpr 记文件 IO，卡死时：

- 一个子进程（pid 12228）读了 **3,207,185 次** `D:\deepseek_h\DeepSeek Harness.exe`
- 它的启动命令是 `...dsh-subprocess-local\lib\runner.js -- git.EXE rev-parse --show-toplevel ...`
- 同期主进程读盘 **1.35 GB/s**，页面错误峰值 **2.5 万次/秒**
- 探活连续超时（每次 2.5 秒）

## 根因

`@deepseek-ai/dsh-workspace-changes` 的 `locateGitWorkspace()` 每次要算「工作区有没有改动」，
就会启动一次 `git rev-parse` 子进程。每启动一次，整个 DeepSeek Harness.exe 和依赖库都要重新载入一遍。
频率高起来，磁盘和内存一起被压住，主进程连探活都答不上来。

不是本地模型，不是显存，也不是插件本身的大小。

## 处置

1. **关掉 `workspace-changes` 插件**（主要）：设置 → 插件 → 关 `@deepseek-ai/dsh-workspace-changes`。
   副作用：`ui-deliverables`（交付文件界面）暂时不可用。
2. 360 安全卫士对 `D:\deepseek_h`、`D:\deepseek_local` 加信任（次要，单独加没有明显效果）。

## 效果

| | 关之前 | 关之后 |
|---|---|---|
| 探活超时 | 5 / 18 条 | 0 / 14 条 |
| 主进程读盘峰值 | 1354 MB/s（持续） | 408 MB/s（瞬时一次） |

## 怎么复查

`node scratch/...` 不必，直接看 `runtime/consciousness/freeze-watch.jsonl`：
每 10 秒一条，带 `ping`、`sys`、`topIO`（含进程角色）。超时多、`host-main` 读盘高，就是它又回来了。

## 如果以后要修得更彻底

不用关插件，而是让 `locateGitWorkspace()` 结果带缓存（同一目录同一个仓库只查一次）。
那要改 DSH 本体，升级会覆盖，先记在这儿。
