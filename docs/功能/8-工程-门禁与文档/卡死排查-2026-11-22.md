# 卡死排查总账（2026-11-22）

> 这一份替代今天散落的五份（git 查询那份、心跳分段计时、两份交接、建图增量）。只留终版结论、证据和教训。

## 症状与判据

界面卡在「正在载入」，几十秒到一分钟，空档不说话时也会发生，最后只能重启。

**判据（重要，今天在这里错过一次）**：

- **真卡死** = 探活超时（`freeze-watch.jsonl` 里 `ping` 2.5 秒超时、`pingFails` 涨）+ 心跳扫描缺席 + 日志空白。
- **不是卡死** = `stall`（hook.log 多久没写）变大但探活正常。没人说话时插件本来就不写日志，`stall` 照样涨。
  今天几次把 `stall` 当卡死读，误判了。

## 三处根因（终版）

三处都在本插件里，形状一样：**纯规则、本该毫秒级的定时活里，塞了一条同步查询，按行扫大表**。
库从几十兆长到 344MB 之后，它们从「察觉不到」涨成「几十秒」。

| # | 位置 | 在干什么 | 修前 | 修后 |
|---|---|---|---|---|
| 1 | `src/modules/ops.js` `auditStore` | 三条全文对账用 `NOT EXISTS(...WHERE f.id=m.id)`；fts5 的 id 是 UNINDEXED 点查不了 → 8255 行 × 5.2MB 整表扫 ≈ 43GB | **34 秒** | **58~68ms** |
| 2 | `src/modules/pulse.js` `queueSurface` | 给每条记忆算「上次浮现时间」(`ORDER BY MAX(...)`) 和「浮现过没有」；`surfaced_items` 59421 行、11.9MB，索引只到 `(agent_id, at)`，没有 `memory_id` | **9896ms** | **7ms** |
| 3 | `index.js` 心跳 `step('graph')` | 每跳把最近 30 天事件两两比一遍建事件底图 | **2108ms** | 调用已移除 |

对应修法：

1. **全文对账改问法**：不再「一行一行问」，改成两边各取一遍 id 集合、在 JS 里求差。读表次数从「记忆行数」降到 2。
2. **补两条索引**（`src/db.js`）：`idx_surf_mem ON surfaced_items(agent_id, memory_id, at)`、`idx_sq_mem ON surface_queue(agent_id, memory_id, state)`。SQL 一个字没改。
3. **建底图整块停用**：判据不可靠（引文 `contains`、标题滑窗都靠猜），函数留着给测试。

## 两个放大器

- **定时器叠加**：`startMaintenance` 的句柄只存在函数里，热重载会再挂一个、旧的照样响——重载几次就有几个体检在跑。改成挂 `globalThis`（`Symbol.for('dsh-consciousness.maintenance')`），新的先清旧的。
- **`lastPurge` 只在内存**：重启归零 → 每个新进程活到 5 分钟必跑一次体检。改成落库 `flags['maintenance.last_purge']`；频率也从 24 小时改成 **7 天**（三项检查一直是 0）。

## 巡检结论（全 src 扫过，2026-11-22 晚）

所有带相关子查询的 SQL 都做了查询计划。内层仍整表扫的只剩三条，都按真库计过时：

| 查询 | 在哪跑 | 内层表 | 实测 |
|---|---|---|---|
| `pickReviewCandidates` | 心跳复查，2 小时一次 | `affect_review` 151 行 | 1ms |
| `pickReappraiseTarget` | 夜里 | `conflicts` 45 行 | 0ms |
| 人格轴迁移 | 开库时一次 | `persona` 19 行 | 一次就完 |

大表单次扫也都在一天一次的活里：`events` 13.4 万行按类型滤 51ms、`fragments` 2.2 万行扫一遍 18ms。

**唯一还没被时间检验的**：`DELETE FROM memory_fts WHERE id=?` 仍是整表扫 5.2MB。平时只在改一条记忆时调一次；**但批量导入 / 回填如果循环调它，就会变成今天这个形状**——将来做批量写入时先看这条。

## 两个工程教训

**一、热重载不重新加载子模块。** 只重新执行入口 `index.js`；`ops.js` / `db.js` / `pulse.js` 走 ESM 缓存，不重新求值。
所以改子模块**必须重启进程**，重载看起来「没生效」不是代码没改，是没加载。验修正确认两件事：值有没有落进库、进程是不是真重启（看进程启动时间，不只看 `apply-enter`）。

**二、写的时候只想了「对不对」，没想到「数据会长」。** 这几处测试都只测功能正确性，没有一处测「库长大一百倍之后还跑得动吗」。同类活以后都该有个以数据量为变量的验收。

## 怎么退

- 体检对账：还原成 `NOT EXISTS(...WHERE f.id=m.id)` 三条（会很慢，不建议）
- 两条索引：`DROP INDEX idx_surf_mem; DROP INDEX idx_sq_mem;`（不动数据）
- 建图：把 `index.js` 里注释掉的 `step('graph', ...)` 接回来
- 体检频率：`7 * 86400000` 改回 `24 * 3600000`
- 单例定时器：删掉 `globalThis` 那几行（会退回「重载叠加」）
