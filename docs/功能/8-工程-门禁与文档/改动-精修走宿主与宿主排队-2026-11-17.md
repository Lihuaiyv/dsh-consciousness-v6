# 改动 · 精修走宿主 + 宿主后台调用排队（2026-11-17）

> 主人原话：「按照这样改吧。宿主调用的应该挺多吧。按照逻辑是不是也要排队？如果是就排，不过注意，不要出现生成顺序的逻辑错误。」

## 一、动了哪

| 文件 | 改动 |

## 二、为什么

- 本地 14B 每轮精修要 2~16 秒，还占一条本地队列（被切事 45 秒的块挡住时，`affect:frame` 实测等过 43 秒）；宿主模型快、准，成本按公开价估算约 **0.2~0.7 元/天**（每轮多一次小调用，300 token 入 / 80 token 出）。
- judge 那一步本来就走宿主（原文早已上云），把事层也搬过来不增加暴露面。
- 后台宿主调用确实会变多（每轮 topic + judge），不排会一次发太多、撞限速；但仓库里原先没有任何宿主并发控制。

## 三、顺序纪律（主人点名的那条）

「不要出现生成顺序的逻辑错误」在代码里的落点：

1. **同一个 agent 串成一条链**：`chains` Map 按 `agent_id` 挂链尾，前一个 settle 才启动下一个。
   所以同一轮的 `affect:topic` 一定在 `affect:judge` 之前执行（judge 依赖 topic 的结果）；
   上一轮的帧一定先落库，不会因为并发反序。
2. **不同 agent 互不阻塞**：每个 agent 一条链，只共享全局并发额度（默认 2）。
3. **闸门不重排**：排队按发起顺序 FIFO，不做优先级插队（本地队列才有优先级；宿主这里顺序优先）。
4. **超时只丢自己**：排队超预算的调用提前失败、立即从队列摘除，不会挡住后面同 agent 的调用。
5. refineShadow 自身还有 `refining` Set：同一 agent 同一时间只跑一个精修，双保险。
6. **精修本身也排队，不丢**（2026-11-17 主人追问后补的）：`refining.has(aid)` 原来直接 `already` 丢弃，
   现在改成 per-agent 链：后来的挂在前一个后面等，按发起顺序执行；队里最多压 5 个
   （主人 2026-11-17 定为 5），第 6 个才丢（`diag=overflow`）。正常打字（几秒一条、每条 2 秒）
   压不满；只有 2 秒内连来六七条那种极端并发才会丢。

## 四、怎么验

```powershell
cd D:\deepseek_local\plugins\dsh-consciousness-v6
node scripts/check-host-queue.mjs      # 12 项：并发≤2 / 同 agent 保序 / 跨 agent 并行 / 排队超时 / 快照
node scripts/check-refine-queue.mjs    # 5 项：并发两轮都跑、两行 model 帧、顺序不乱、四次调用、不算 already

```

验收基线：4 个任务并发最大 2；`X:1` 慢任务后排的 `X:2` 严格等它结束（顺序 `start1,end1,start2,end2`）；
两个 agent 可同时跑；预算 1000ms 的第三个调用在 ~1s 被拒且没执行；快照名字/等待/耗时都在。

真实使用：会话里调 `local_llm_status`，会看到「宿主后台 并发 2 · 在跑 x · 在排 y」和最近几条 `affect:topic/judge`。

## 五、怎么退

1. 只想回本地：把 `affect.engine.shadow.topic` 设成 `local`（参数，不用改代码）。
2. 只想关宿主闸门：把 `hostComplete` 的直接调用改回 `kernelModel.complete(...)`（两处：topic / judge）。
3. 宿主并发调大/调小：`llm.host.concurrency`（默认 2）。
4. 不影响：数据库结构、本地队列（local_llm.js）都没动；精修开关 `affect.engine.shadow.model` 仍是 on。

## 六、补充（2026-11-17 13:03）：判断解析失败先重试宿主

现象：`judge-host-unparsed` 反复出现，raw 断在 `"expectation":0.`；解析失败后直接回退本地 14B，一帧 6~15 秒。

改法：
- 判断的宿主调用**失败先重试一次**（1~2 秒），两次都解析不出来才回退本地；重试也在同一 agent 链上，不乱序。
- 诊断 raw 从 80 字扩到 400 字，并带 `len`，能看出是截断还是格式坏。
- 判断 `maxTokens` 300 → 500（留余量）。

验证：`check-refine-queue` 7 项全过；门禁 588 / 588。
