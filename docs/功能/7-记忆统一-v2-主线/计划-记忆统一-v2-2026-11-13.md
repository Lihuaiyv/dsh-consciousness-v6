## L0 目标层：事件做中心，什么算成

**为什么偏事件**：记忆的单位该是「一件事」——碎片只记发生过什么，事实是几件事沉淀的结论，日记是讲那几天怎么过的。**事件在中间，上面能蒸馏成事实，下面能追回原话。**

七条验收沿用 v1，但中心判定加一条**硬信号**，并修正 v2 里数错的基线：

| # | 验收 | 怎么算 |
|---|---|---|
| 0 | **事能自己长出来** | 回填日不计；回填次日起，每天新增 ≥5 件 |
| 1 | 同一句话最多 2 份 | 原话 + 事；不再有每轮 episode |
| 2 | 旧事问得起 | 10 题答对 ≥8 |
| 3 | token 中位不涨 | 800 / 400 / 1600 单开 |
| 4 | 每轮想起 ≤1 条 | 一天 4~5 次 |
| 5 | 一周库增量降 ≥50% | 观测白名单 + 停重复写 |
| 6 | 老数据与照片不删 | scene_archive/state_scene 只读 |
| 7 | 每步能回旧路 | 开关可切 |

**基线更正（v2 写错的）**：不是「~450 条/天 episode」，实测是 **episode 74 条/今日（11-12 428、11-11 510）**，`memory_items` 24h 总增约 450 是含抽取/事实的。所以目标不写「450→30」，改成：**episode 归零 + 总量先测一周基线再定目标**。
`extract_queue` 也不是 1,959 积压：现 **452 pending / 3,437**，worker 每 30 秒吃一条，自己在掉——**不是积压项，只需盯消化速率**。

**失败信号**：事件库长期少于每天 3 件，或某个 7 天窗口没有新事件——**那"中心"是空的，计划作废**。

## L1 架构层：事件中心图

```
你说了什么
  │
  ├─ 碎片 fragments（原料，只追加：谁、何时、说了什么、当时什么样、接自谁）
  │        │
  │        └─ 夜里切 → 事（冷库→热库）
  │              名字 / 经过 / 证据 / 抓手 / 想头 / 天花板 / 状态
  │
  ├─ 事实库（事的沉淀：跨事成立的才留）
  │       身份 / 偏好 / 边界 / 结论 / 自我
  │       memory_items(fact/reflection/self) + fact_archive(版本) + provenance(证据)
  │       + timeline(有效期) + claims(还算不算)
  │
  ├─ 叙事（事的讲述：日记 / 纪要）  只引用事件与事实，不产生新事实
  │
  └─ 读口 planner
         模式一 检索  模式二 联想  模式三 汇流
```

**追溯**：事实 → 事 → 碎片；日记 → 事 → 碎片，两跳到底。
**边界**：碎片是地基，不是中心；事实是蒸馏，不是记录；日记是讲述，不是真相。

## L2 契约层：事件中心后的变化点

### 2.1 事件层（中心）——**先补"切→导→热"整链**

现状（审计核实）：`splitDay` 只把 JSON 写出去、不入库（event_split.js:277-285）；输出是 `{results:[{events}]}`，导入器却按数组吃（import-cold-events.mjs:47）；热库还要手加 `--hot`；**没有定时任务**（全仓只有 api.js:969 调它）。

所以这一层先立三条：

- **写入器**：定时任务直接写 `cold_events` + `hot_events`，不走 JSON、不靠手跑脚本。
- **时刻**：23:00 的定时器在 `host/workers.js:112,166-184`（nightly.js 只是被调函数），**跨零点切"前一天"要在这里落地**，不是另起一个凌晨 cron。
- **幂等**：同一段碎片只允许一条冷事件；重切/改名不新增行（现 id = sha1(title,started_at,首末 turn)，会重复）。
- **质量硬门**：每条 2~6 个抓手、至少一个专名；`checkEvent`/导入器校验，无抓手就重切或拒收（现 checkEvent 不校验 cues，import 允许 null，recall 遇 null 直接跳过）。

每条事仍须：≥1 段连续碎片、≥1 句逐字原话、3~5 个抓手；补切只追加；沉底只动热库。

### 2.2 事实层（事件的蒸馏）

- **只有能指回一件真实事件（或一条碎片原话）的结论，才许进事实库**；指不回去的，是猜，不进。
- 带证据、有效期、版本、对账状态；日记/纪要/pulse 不许直接写事实。
- **空窗期退回**：episode 停写后、事件还没覆盖当天之前，检索的空窗由 fragments 兜底（读口写死这条退路）。

### 2.3 叙事层（事的讲述）

- 日记/纪要只引用事件与事实；日记里一句话要能指回事件。
- 日记可以有自己的判断，但那是讲述，不冒充事实。

### 2.4 读口与预算——**不是"一个拼装器"，是两个**

审计核实：`consciousnessBlock`（index.js:758，网页）和 `buildContextBlock`（features.js:1484，/chat、微信、QQ）各自拼提示词；**事件联想只在 index.js:1730 接线，chatReply 里没有 recallEvents**。所以契约写成：

- **两个拼装器共用同一个候选池、同一张预算表**；谁先谁后可以不同，取数规则只能一套。
- 一轮最多一条"自己想起"；预算：日常 800 / 事件 400 / 汇流 1600（手动才开）。

### 2.5 id（不变）

`turn_id` 是血缘；聊天账补 `turn_id`（老行 null）；事件 id 自成一族（`cev_`/`hev_`），证据存碎片 id。

### 2bis. 切事分两个标准（2026-11-13 主人定调）

- **日常（daily）**：仍是原来的标准——逐件切、引文/轮次/抓手硬校验、质量优先；B2 只把「一件一调」改成「一块一切」省调用次数，**切的标准不降**。
- **工作（work）**：**轻模型**——按**字数**切段（每段输入 ≤8k~12k 字，≈4k~6k tokens；60~100 轮只是参考，长轮次段要再切）、短提示（只要「这段在做什么」≤100 字 + 3~5 个抓手）、低输出上限（≤300 tokens）；不要求逐件证据，不做精读。规则分段只在没额度时兜底（0 成本，且不产事实）。
- **混天**：一天里两种模式都有时，按 `chat_turns.mode` 把 turns 分成 work 段和 daily 段，分别用各自标准切。

**代价估算（2026-11-13 下午修正）**：
- 批量块别用 30~40 轮——事件稀疏的一天，顺序切只要 ~13 次调用，30~40 轮一块反而要约 40 次，**更贵**。daily 段按 **120~150 轮一块、一块要 3~5 件** 算，一天约 **10~15 次调用**。
- work 段走规则：**0 次模型调用**。工作日省下的大头在这里。
- **硬顶分两层**（2026-11-13 修正）：自动 worker = 15 次/天（防睡着时偷偷烧钱）；**手动/回填 = 60 次/次**（一天的活一天干完，不再摊到 3 天）。
- 结论：真正省的不是「批量」，是 **work 段不花钱 + 只切有内容的段 + 自动兜底硬顶**；手动回填按次算，不按天拖。
