## 写文档之前：先看 `docs/形式/`

**写任何新文档之前，先来 [docs/形式/](形式/README.md) 挑一种形式。**

目前有一种：**[夯实](形式/形式-夯实-2026-11-15.md)**——主人写一句、我进一步，一句一钉，错步不删。用在有骨头的问题上（定义、容易被我磨圆的讨论），不用在交付清单上。

## 写新文档的规矩（2026-11-14 改）

1. **根上只放三份入口**（INDEX / README / ARCHITECTURE），新文档别往根上扔。
2. **先想它属于哪个功能**，放进 `docs/功能/<功能>/`，名字带日期（`设计-…` / `计划-…` / `改动-…` / `交接-…` / `工具-…`）。
3. **写完更新那个功能目录的 `README.md`**：改「现在到哪」那一句和「完整链条」表，别让索引和事实分家。
4. 一个改动同时碰几个功能，主记录放主要那个，其余功能 README 里加一行链接。
5. 旧稿被取代时，在文件头写「已被取代，见 XX」，别让它装成现状。
6. 移动文档时一起修链接——`docs/` 里的相对链接不会自己跟着走。

## 怎么读（2026-11-24 体检后）

- **现行版**：每个功能目录 README 末尾的「现在该读哪几份」就是入口，按改动时间挑的，最多五份。
- **`改动-*.md` 是过程流水**（现有 171 份），记录当时怎么改的，不必通读；要结论看设计/计划/图。
- **`archive/` 只作证据**，每个子目录的 README 已写明「不要当现状读」。
- 同一主题有多份时（例如 `切出来v4`、`情绪链`），功能目录里**最新那份**是现行版，更早的在 `archive/`。
